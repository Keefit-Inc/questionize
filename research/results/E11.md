# E11: upload-driven memory, first live operator cycle

## What actually ran

The production learner API accepted an original synthetic image contract using a dedicated operator-only device, not a learner's account. The running Meta service separated reference material, answered in two isolated calls, produced a diagnosis and recorded an abstract observation under pinned solving memory v1. Both independent answers matched the supplied reference. Source material was saved in a private local file, then the delivery cache was acknowledged and verified unavailable. No practice items were generated and no source question entered the public Bank.

A separate, explicitly labeled operator audit contributed an actual Solver failure observed in E10 v2. Only the normalized source-group fingerprint, reference-confidence category, abstract role-confusion lesson and correctness flags were sent to the service. The original question, reference key and publisher explanation remained local. This historical audit is not represented as a new learner upload.

The batch automatically queued cycle `524e3c74907182cd`. The registered private Mac worker leased it, generated a candidate with Meta, froze its version and evaluated it using fresh inference on disjoint local source-keyed questions. It proposed three expert-reference-derived procedural rules and no additional experience-specific rules. Actual rule contents and teacher material remain private.

No improvement was reproduced. The service therefore **held candidate v2 and retained active memory v1**, whose two rule namespaces are empty. Candidate generation plus evaluation completed 65 logical model calls (one proposal and 64 solving calls). All calls used `muse-spark-1.3`; this is separate context, not separately trained model independence.

The local corpus had 70 source-keyed training groups. Sixteen validation items covered eight subtypes. Training groups and the triggering historical source group were excluded from validation. Teacher examples were selected only from training. The local registration, teacher context, candidate, exact Python source snapshot and individual model outputs are private artifacts. The server received rule payloads, hashes and paired correctness flags, not question text or answer-key corpora.

The evaluated worker source revision was `d2c1afb99d8b838056824c1a00ab64dce8ee7e0b`. A later spelling normalization for inferred subtype tags prevents `Inference`/`inference` mismatches during teacher-example retrieval; it does not change the blind solving method or retroactively change this run.

## Scope of the evidence

This proves a live operator path through observation ingestion, automatic scheduling, real Meta proposal, fresh paired local evaluation, a justified hold, and retention of the operating version. It does **not** establish an accuracy gain. There were zero real learner uploads in this first operator validation; operator records are counted separately in the console.

Adoption, request pinning, failed-service rollback, later confirmed-source rollback, contaminated-validation rejection and curator-only rule access are also covered by offline scripted integration tests. Those tests demonstrate branches, not live model improvements. No live adoption is claimed for this run.

The validation pack is a reused development/pilot benchmark, not an untouched external holdout. Two passes on the same sixteen items are correlated. There is no 99.9% reliability certification, human explanation-quality measurement, generation-quality improvement or learner-growth result here.

## Operation and privacy

`/admin#uploads` shows live heartbeat, source confidence, candidate progression, both evaluation passes, decision reasons and the active memory hash. Curators can inspect private candidate procedures after authentication; public data contains only counts, hashes and aggregate evidence. The running service's shared solver uses the request-pinned immutable memory. A Mac outage delays research while normal hosted learner analysis continues.

Terminal measurement rows are frozen and appended through the existing ledger export; later operating rollback does not rewrite experimental history. The scoreboard uses the first pass's sixteen-item score and records E11 as a trial/pilot, separate from full E9 evaluations and E8 recorded replay. The second pass is a separate replication gate, not another sixteen independent test items.
